# Verification matrix and repair loop

Read the actual project's existing compliance requirements and executable gate first. Extend them for the requested scope without resetting failures. No evidence from another website may qualify this one.

| Category | Minimum meaningful observations |
|---|---|
| identity | Current canonical ID, editor URL, source/deployment revision; verified session belongs to this site |
| research | Dated official docs, terms, used skills, licenses; two concepts and three inspected references for major design |
| design-system | Shared tokens/styles, named section/component inventory, actual repeated instances and preserved owner feedback |
| customization | Real native controls, buyer default insertion, long/empty copy, image replacement, extreme legal controls and coherent variants |
| responsive | Actual phone/tablet/desktop, intermediate and breakpoint +/-1px, minimum width, landscape, 200% zoom, no unintended clipping/overflow |
| forms | Labels/constraints/states, invalid/corrected/valid input, pending/retry and approved delivery evidence where applicable |
| content-localization | CMS empty/long/missing content, filters/pagination, Arabic/RTL where used, stable identifiers and real detail routes |
| accessibility | Keyboard order, focus visibility/return, touch targets, semantics/contrast, errors, reduced motion; automated and manual |
| motion | Purpose/property ownership, section coordination, static/server visibility, touch/reduced/disabled states, lifecycle cleanup |
| performance-images | Reproducible repeated mobile profiles, actual image delivery/quality, measured bytes/requests, startup/idle/interaction cost |
| seo-routes | Actual metadata and initial HTML, direct locale/CMS routes, internal links, back/forward, canonical/indexing, sitemap/404/redirects |
| code-diagnostics | Actual Framer diagnostics and runtime logs, SSR/hydration, types/build when code applies; no suppression |
| rights-privacy | Asset/font/component/dependency provenance and exact use grant, attribution, real form/data flow and secrets boundary |
| editor-preview | Actual editor visuals and native edits plus separate Preview interactive observations at representative sizes |
| deployment | Exact authorized artifact, optimization warnings/errors, public first load and runtime, not prepublish readiness alone |
| documentation | STATUS, DESIGN, research/compliance, issue log, buyer guide, controls and native skill payloads where useful |

Example viewport starting set: 320, 390, 768, 810, 1024 and 1440px, plus each actual breakpoint boundary and content-driven widths. These are suggested test defaults, not Framer requirements. Include every relevant page family and shared consumer. Adapt to a documented supported range, never remove a failure by narrowing it silently. Document the browser/device matrix from audience risks. Test Safari/iOS when relevant to mobile menus, gestures, autoplay or effects. Emulation and headless WebKit are approximations, not proof of physical iOS behavior; missing required device evidence stays explicit.

Create a defects table with ID, reproduction, surface/viewport/state, expected/observed behavior, severity, revision, evidence, owner and status. Small design defects still block acceptance. For each fix rerun the original reproduction and affected shared consumers, then refresh changed evidence. Preserve failed logs and superseded revisions as history. Do not rewrite old failures into passes.

Visual review must assess typography, hierarchy, spacing rhythm, composition, image crop/contrast, coordinated motion, touch usability and buyer value. Machine checks cannot replace it. Use actual screenshots and interactive observations. Screenshot-only review must state the behaviors it cannot prove.

For a scoped repair report the changed surface's checks and broader unresolved site gates separately. For a release run every required category, record applicability and block on known issues/warnings/missing/stale evidence. Owner-approved scope/field-data decisions must be explicit with source and practical limits. Acceptance never means proof of zero undiscovered defects.

An unpublished task can finish its authorized local work while deployment acceptance remains blocked. Honor existing publication authority. Post-deployment checks can only pass after inspection of the actual deployment; a pre-release checkpoint is a separate status.
